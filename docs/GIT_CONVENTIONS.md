## Модель ветвления

Используем **GitHub Flow**:

- `main` — единственная постоянная ветка. Всегда стабильна и готова к деплою.
- Вся работа ведётся в коротких feature-ветках, которые создаются от `main` и вливаются обратно через Pull Request.

```
main
 ├── feature/123-add-jwt-auth
 ├── fix/456-user-not-found-error
 └── chore/789-update-dependencies
```

> Прямые коммиты в `main` запрещены. Любое изменение — через PR.

## Именование веток

### Формат

```
<тип>/<issue-id>-<краткое-описание>
```

- `<тип>` — категория изменения (см. таблицу ниже)
- `<issue-id>` — номер задачи из GitHub Issues
- `<краткое-описание>` — 2–5 слов через дефис, строчными буквами, на английском

### Типы веток

| Тип | Когда использовать |
|---|---|
| `feature` | Новая функциональность |
| `fix` | Исправление бага |
| `chore` | Рутина: зависимости, конфиги, CI |
| `refactor` | Рефакторинг без изменения поведения |
| `docs` | Только документация |
| `test` | Добавление или исправление тестов |

### Примеры

```
feature/42-add-jwt-authentication
fix/87-fix-null-pointer-in-user-service
chore/103-upgrade-spring-boot-3-2
refactor/61-extract-email-validation
docs/15-add-api-usage-examples
test/99-add-integration-tests-for-auth
```

### Правила

- Только строчные буквы и дефисы, без пробелов и спецсимволов
- Описание на английском языке
- Без номера issue ветку не создавать — сначала заводим задачу

## Коммиты

Используем спецификацию **[Conventional Commits](https://www.conventionalcommits.org/)**.

### Формат

```
<тип>(<скоуп>): <описание>

[тело — опционально]

[футер — опционально]
```

### Типы коммитов

| Тип | Когда использовать |
|---|---|
| `feat` | Новая функциональность |
| `fix` | Исправление бага |
| `chore` | Рутинные задачи, не влияющие на код продукта |
| `refactor` | Рефакторинг без изменения поведения |
| `docs` | Изменения в документации |
| `test` | Добавление или изменение тестов |
| `perf` | Улучшение производительности |
| `ci` | Изменения в CI/CD конфигурации |
| `style` | Форматирование, пробелы (не влияет на логику) |

### Скоуп (опционально)

Указывает на область изменения: `auth`, `user`, `order`, `db`, `api` и т.д.

### Правила

- Описание на английском языке
- Строчная буква в начале, без точки в конце
- Длина заголовка — не более 72 символов
- Используй повелительное наклонение: `add`, `fix`, `update` — не `added`, `fixed`, `updated`
- Тело коммита — объясняй **почему**, а не что (что видно из diff)

### Примеры

```
feat(auth): add JWT token refresh endpoint

fix(user): return 404 when user not found instead of 500

chore: upgrade spring-boot to 3.2.1

refactor(order): extract price calculation to separate service

docs(api): add examples for authentication endpoints

test(auth): add integration tests for token expiration

feat(auth)!: replace session auth with JWT

BREAKING CHANGE: session-based authentication removed,
all clients must use Authorization header with Bearer token
```

> `!` после типа и `BREAKING CHANGE:` в футере обозначают breaking change.

## Pull Request

### Когда открывать PR

- Ветка готова к ревью — вся запланированная работа сделана
- Есть тесты на новую/изменённую логику
- Код локально собирается и все тесты проходят

### Оформление PR

**Заголовок** — по формату Conventional Commits:
```
feat(auth): add JWT token refresh endpoint
```

**Описание** — используй шаблон:

```markdown
## Что сделано
Краткое описание изменений.

## Связанная задача
Closes #<номер issue>

## Как проверить
1. Шаг первый
2. Шаг второй
3. Ожидаемый результат

## Скриншоты / логи (если применимо)
```

### Процесс

1. Создать ветку от актуального `main`
2. Разработать, написать тесты, убедиться что CI зелёный
3. Открыть PR, заполнить описание, назначить ревьюера
4. После апрува — смёржить через **Squash and merge**
5. Удалить ветку после мёржа

### Правила

- Минимум **1 апрув** для мёржа в `main`
- Все CI-проверки должны быть зелёными
- Автор PR сам мёржит после получения апрува
- Не мёржить PR с неразрешёнными комментариями
- Стратегия мёржа: **Squash and merge** — один чистый коммит в `main` на каждый PR

### Размер PR

Стремиться к небольшим PR — их легче ревьюить и безопаснее мёржить:

| Размер | Строк изменений | Рекомендация |
|---|---|---|
| Идеальный | до 200 | 👍 |
| Допустимый | 200–400 | Окей, но постарайся разбить |
| Большой | 400+ | Обсуди с командой, скорее всего можно разбить |

> Исключение: автоматически сгенерированные файлы (миграции, OpenAPI-схемы).

### Hotfix

Если нужно срочно починить баг в `main`:

1. Создать ветку `fix/<issue-id>-<описание>` от `main`
2. Минимально необходимое исправление, тест на баг
3. PR в обычном порядке — ускоренное ревью (договориться с командой)
